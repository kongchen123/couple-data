# 第19章 配置管理与变更管理 · 重点知识点

> 第4版教材第19章 · 综合知识 3~4 分 · 案例高频（配置项、版本混乱）

---

## 一、定位：配置管理是"管物件"，变更管理是"管流程"

**两个概念的本质区别**

| | 配置管理（Configuration Management） | 变更管理（Change Management） |
|---|---|---|
| 管什么 | **配置项**（产品、文档、代码）及其**版本** | **变更请求**的全流程 |
| 核心问题 | "这东西是哪个版本？谁改了？" | "这个改动该不该做？谁批准？" |
| 关键活动 | 识别、控制、记录状态、审计 | 申请、评估、审批、实施、验证 |
| 类比 | 图书馆的书籍编目与版本 | 借书审批流程 |

> 关键论断：**配置管理是变更管理的基础**——没有清楚的配置项和版本，变更就无从谈起。

## 二、配置管理核心知识

### 19.1 配置项（Configuration Item, CI）

**定义**：**纳入配置管理**的工作产品，是配置管理的基本单位。

**常见配置项**
- 项目管理计划、项目文件
- 需求文档、设计文档
- 源代码、可执行程序
- 测试用例、测试报告
- 用户手册、运维手册
- 硬件、工具、环境配置

> 判断标准：**需要控制版本、需要多人共享、变更需受控**的东西，都应纳入配置管理。

### 19.2 基线（Baseline）

**定义**：**经过批准的、作为后续工作依据**的配置项版本。

**三类基线（按项目阶段，必背）**

| 基线 | 建立时机 | 包含内容 |
|---|---|---|
| **功能基线**（需求基线） | 需求分析完成后 | 需求规格说明书 |
| **分配基线**（设计基线） | 概要设计完成后 | 设计文档 |
| **产品基线** | 产品交付前 | 完整产品及文档 |

> 另有**发布基线**（每次发布时的快照）。基线一经建立，**变更必须走变更控制流程**。

**基线的三个特性**
- **基线化后的配置项不可随意修改**
- 基线是**评审和验收的依据**
- 基线可以**演进**，但每次演进都要形成新基线

### 19.3 配置管理的四大活动（必背）

```
① 配置项识别（Configuration Identification）
   确定哪些是配置项、如何命名、如何编号

② 配置控制（Configuration Control）
   控制配置项的变更（与变更管理联动）

③ 配置状态记录（Configuration Status Accounting）
   记录并报告配置项的状态与变更历史
   —— 回答"现在是什么版本、改过什么"

④ 配置审计（Configuration Audit）
   验证配置项的实际状态与记录是否一致
```

**配置审计的两种类型（易考）**

| 类型 | 全称 | 检查什么 | 时机 |
|---|---|---|---|
| **功能配置审计（FCA）** | Functional Configuration Audit | 配置项**是否实现了需求**（功能、性能） | 交付前 |
| **物理配置审计（PCA）** | Physical Configuration Audit | 配置项**是否与文档一致**（"按图核对"） | 交付前 |

> 记忆：**FCA 看"功能对不对"，PCA 看"东西全不全、和文档一致不一致"。**

### 19.4 配置库（Configuration Library）

**三类配置库（必背）**

| 类型 | 存放内容 | 权限 |
|---|---|---|
| **开发库（动态库）** | 开发过程中的**工作版本**，频繁变更 | 开发人员自由读写 |
| **受控库（主库）** | **基线化**的配置项 | 受配置控制，**变更需审批** |
| **产品库（静态库）** | **已发布**的最终产品 | 只读，任何人不得修改 |

> 记忆：**开发库随便改，受控库审批改，产品库存着不改。**

**配置项的生命周期**
```
开发库（工作中）→ 评审通过 → 受控库（基线化）→ 发布 → 产品库
```

### 19.5 版本管理

**常见版本命名**
- 主版本.次版本.修订号（如 `2.1.3`）
- 主版本：架构级变更
- 次版本：功能新增
- 修订号：缺陷修复

**关键实践**
- 每次发布必须**打标签（tag）**
- 保留**变更历史**，可回溯任意版本
- 严禁直接修改**产品库**中的版本

## 三、变更管理核心知识

### 19.6 变更管理的组织

| 角色 | 职责 |
|---|---|
| **变更申请人** | 提出变更请求，说明理由 |
| **项目经理** | 评估影响、组织分析、在授权范围内批准、实施变更 |
| **CCB（变更控制委员会）** | **决策机构**，审查、批准、推迟或否决变更 |
| **配置管理员** | 记录变更、维护配置状态、执行配置审计 |

**CCB 的性质（必考）**
- 是**决策机构**，不是执行机构——**CCB 批准变更，但不负责实施**
- 成员：发起人、客户代表、项目经理、技术专家、关键干系人
- 职责：**审查、评价、批准、推迟或否决**变更，并**记录和传达**决定

### 19.7 变更流程（六步，与整合管理一致）

```
① 提出变更申请
   - 任何干系人都可提出，可口头提出但必须书面记录
   - 记入变更日志

② 分析变更影响
   - 范围、进度、成本、质量、风险各维度
   - 给出备选方案与建议

③ 提交 CCB 审批
   - 批准 / 推迟 / 否决
   - 记录并传达决定

④ 实施变更
   - 更新项目管理计划与项目文件
   - 通知相关干系人

⑤ 验证变更效果
   - 确认达到预期目标
   - 必要时进行缺陷补救

⑥ 结束变更
   - 归档变更记录
   - 更新经验教训登记册
```

### 19.8 变更控制与配置控制的关系

```
变更管理（管流程）              配置管理（管物件）
    提出变更请求
         ↓
    影响分析 ──────────────→ 检查配置项当前状态
         ↓
    CCB 审批
         ↓
    实施变更 ──────────────→ 更新配置项，形成新基线
         ↓
    验证效果 ──────────────→ 配置审计（FCA/PCA）
         ↓
    归档记录 ──────────────→ 配置状态记录更新
```

> 关键：**两者是配合关系**。变更管理决定"改不改"，配置管理记录"改成了什么版本"。

## 四、高频易错对照表

| # | 陷阱 | 正解 |
|---|---|---|
| 1 | 配置管理就是变更管理 | 配置管**物件与版本**，变更管**流程与审批** |
| 2 | 基线建立后可以随意修改 | 基线变更**必须走变更控制流程** |
| 3 | FCA 检查文档一致性 | **FCA 检查功能是否实现**；PCA 检查物理一致性 |
| 4 | 产品库可以修改 | 产品库**只读**，禁止修改 |
| 5 | 受控库可由开发人员自由读写 | 受控库**变更需审批** |
| 6 | 开发库是基线存放处 | 开发库存**工作版本**，受控库才是基线 |
| 7 | CCB 负责实施变更 | CCB 是**决策机构**，不负责实施 |
| 8 | 配置项只是源代码 | 配置项包括**文档、计划、代码、测试用例、环境配置**等 |
| 9 | 口头变更即可 | 可口头提出，但**必须书面记录** |
| 10 | 基线只有一种 | 功能基线、分配基线、产品基线（还有发布基线） |
| 11 | 配置审计只在项目结束时做 | 可在**里程碑、交付前**多次进行 |
| 12 | 变更批准就算完成 | 还要**实施、验证、更新基线、归档** |
| 13 | 配置管理员负责批准变更 | 配置管理员负责**记录与审计**，批准由 CCB/PM 决定 |
| 14 | 配置状态记录只记最终版本 | 要记录**完整变更历史**，可回溯任意版本 |

## 五、案例题万能模板

```
问题：
1. 未建立配置管理计划，配置项不明确
2. 未识别配置项，文档与代码版本混乱
3. 未建立基线，或基线建立后随意修改
4. 开发库、受控库、产品库混用，权限不清
5. 变更未经 CCB 审批即实施
6. 变更未评估影响，导致范围/进度/成本失控
7. 变更实施后未验证效果，未更新基线
8. 未开展配置审计，实际状态与记录不一致
9. 缺少变更日志与配置状态记录，无法追溯

措施：
1. 编制配置管理计划，明确配置项识别规则与命名规范
2. 识别全部配置项（文档、代码、测试用例、环境等）并纳入管理
3. 在关键节点建立功能基线、分配基线、产品基线，基线变更走审批
4. 建立三类配置库并明确权限：开发库（读写）、受控库（审批）、产品库（只读）
5. 建立 CCB 并明确职责，所有变更提交 CCB 审批
6. 变更前做多维度影响分析（范围/进度/成本/质量/风险），给出备选方案
7. 变更实施后验证效果，更新配置项并形成新基线
8. 定期开展配置审计（FCA 检查功能、PCA 检查一致性）
9. 建立变更日志与配置状态记录，保证全程可追溯
```

## 六、论文要点（论配置管理 / 论变更管理）

**结构**：背景 300 字 → 过程论述 1500 字 → 问题与解决 400 字 → 总结 200 字

**必须体现的加分项**
- **一次真实的版本混乱事故**：生产环境部署了错误的版本 → 建立三类配置库 + 发布标签机制解决
- **基线的实际作用**：需求基线确认后，客户新增需求必须走变更，避免了 3 次范围蔓延
- **配置审计的发现**：PCA 发现 5 个模块的部署包与文档不一致，及时纠正
- **变更数据的量化**：项目期间受理变更 47 项，批准 31 项、否决 9 项、推迟 7 项
