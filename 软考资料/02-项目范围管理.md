# 项目范围管理 · 重点知识点

> 第4版教材第9章 · 6 个过程 · 综合知识 3~4 分 · 案例高频（范围蔓延、需求不清）

---

## 一、定位：范围管理的本质是"防蔓延"

**核心定义**：范围管理是定义并控制**哪些工作包含在项目内、哪些不包含**的过程。

**两个"范围"必须区分**

| 概念 | 含义 | 对应文档 |
|---|---|---|
| **产品范围** | 产品/服务应具备的**特性和功能** | 需求文件 |
| **项目范围** | 为交付产品**必须完成的工作** | 项目范围说明书、WBS |

> 判断标准：**产品范围对不对看需求，项目范围够不够看 WBS。**

**范围管理全过程逻辑**

```
规划范围管理（定规则）
   ↓
收集需求（要什么）
   ↓
定义范围（做什么，出范围说明书）
   ↓
创建 WBS（拆成工作包，出范围基准）
   ↓
确认范围（客户验收，正式接受）
   ↓
控制范围（防蔓延）
```

**6 个过程与过程组分布**

```
规划 ─── 规划范围管理、收集需求、定义范围、创建 WBS
监控 ─── 确认范围、控制范围
```

## 二、六个过程总表

| 过程 | 过程组 | 关键输入 | 关键工具 | 关键输出 |
|---|---|---|---|---|
| **规划范围管理** | 规划 | 项目章程、项目管理计划、EEF、OPA | 专家判断、数据分析、会议 | **范围管理计划**、**需求管理计划** |
| **收集需求** | 规划 | 立项管理文件、项目章程、项目管理计划、项目文件、协议、EEF、OPA | **头脑风暴、访谈、焦点小组、问卷调查、标杆对照、原型法**、名义小组、观察与交谈、投票、多标准决策、亲和图、思维导图、系统交互图 | **需求文件**、**需求跟踪矩阵** |
| **定义范围** | 规划 | 项目章程、项目管理计划、项目文件、EEF、OPA | 专家判断、**产品分析**、备选方案生成、引导式研讨会 | **项目范围说明书**、项目文件更新 |
| **创建 WBS** | 规划 | 项目范围说明书、需求文件、EEF、OPA | **分解**、专家判断 | **范围基准**、项目文件更新 |
| **确认范围** | 监控 | 项目管理计划、项目文件、工作绩效数据、**核实的可交付成果** | **检查**、决策 | **验收的可交付成果**、工作绩效信息、变更请求 |
| **控制范围** | 监控 | 项目管理计划、项目文件、工作绩效数据、OPA | 数据分析（**偏差分析、趋势分析**） | 工作绩效信息、变更请求、项目管理计划更新、项目文件更新 |

**三条容易记错的点**
1. **确认范围**的输入是"**核实的可交付成果**"（由控制质量产出），输出是"**验收的可交付成果**"
2. **创建 WBS** 才产出**范围基准**（= 范围说明书 + WBS + WBS 词典）
3. 需求收集的工具最多，**原型法、观察与交谈、系统交互图**都是收集需求独有

## 三、逐个重点

### 9.2 规划范围管理

**两个计划**

| 计划 | 内容 |
|---|---|
| **范围管理计划** | 如何定义、制定、监督、控制和确认范围；**如何创建 WBS**；如何维护和批准范围基准 |
| **需求管理计划** | 如何分析、记录、管理需求；需求优先级排序方法；**如何配置需求**（需求变更流程） |

> 易错：**需求管理计划是范围管理过程的输出**，不是收集需求的输出。

---

### 9.3 收集需求

**需求分类**

| 类型 | 说明 |
|---|---|
| **业务需求** | 组织的高层级需要（为什么要做） |
| **干系人需求** | 具体干系人的需要 |
| **解决方案需求** | **功能需求**（产品要做什么）+ **非功能需求**（性能、安全、可用性等） |
| **过渡和就绪需求** | 临时能力（如数据迁移、培训） |
| **项目需求** | 项目自身的要求（如里程碑、质量要求） |
| **质量需求** | 验收标准与验证方法 |

**工具速记（按用途分组）**

| 用途 | 工具 |
|---|---|
| **群体创意** | 头脑风暴、名义小组、亲和图、思维导图 |
| **深入访谈** | 访谈、焦点小组、观察与交谈 |
| **大规模收集** | 问卷调查（受众广）、标杆对照 |
| **需求确认** | 原型法、引导式研讨会（跨职能协调） |
| **结构化表达** | 系统交互图（范围与边界）、需求跟踪矩阵 |

> **焦点小组** vs **引导式研讨会**：焦点小组是同职能/同类干系人；引导式研讨会是**跨职能**协调差异、快速定义需求。

**需求跟踪矩阵（RTM）**
- 作用：把每个需求**从来源追溯到可交付成果**，确保需求被实现和验证
- 包含：需求标识、需求描述、来源、优先级、WBS 关联、测试/验证方法、当前状态

---

### 9.4 定义范围

**项目范围说明书（6 项核心内容，必背）**
① **产品范围描述**（产品特性与功能）
② **可交付成果**（要交付什么）
③ 验收标准
④ 除外责任（**明确不做什么**— 防蔓延的关键）
⑤ 项目制约因素
⑥ 项目假设条件

> 记忆抓手：**产品—交付—验收—除外—制约—假设**

**产品分析**：用于把高层级产品描述转化为详细产品需求。含产品分解、系统分析、需求分析、系统工程、价值工程、价值分析。

---

### 9.5 创建 WBS

**WBS 的定义**：以**可交付成果**为导向的**层级分解**，把项目工作分解为更小、更易管理的组件。

**关键规则**
- 分解的是**可交付成果**，不是"活动"（活动是进度管理的事）
- **最底层是工作包**，工作包再往下分解就是"活动"（属进度管理）
- **工作包**是 WBS 的最低层级，用于估算成本与工期
- **控制账户（CA）**：管理控制点，每个 CA 至少包含一个工作包
- **规划包**：工作内容已知但详细进度尚未确定，位于 CA 之下
- **100% 原则**：子层级之和必须等于父层级 100%，不能多也不能少

**分解步骤**
① 识别可交付成果与相关工作
② 确定 WBS 的结构与编排方法
③ 自上而下逐层分解
④ 为 WBS 组件分配标识编码
⑤ 核实分解程度是否恰当
⑥ 制定 WBS 词典

**WBS 词典**：每个组件的详细描述——账户编码、工作描述、假设与制约、责任人、进度里程碑、成本估算、验收标准、质量要求、技术参考文献、协议信息。

**范围基准 = 项目范围说明书 + WBS + WBS 词典**

---

### 9.6 确认范围

**核心**：**客户/发起人对已完成可交付成果的正式验收**。

| 对比项 | 确认范围 | 控制质量 |
|---|---|---|
| 关注 | **可交付成果是否被客户接受** | **成果是否符合质量标准** |
| 执行者 | 客户、发起人（**外部**） | 项目团队（**内部**） |
| 时点 | 每个可交付成果完成时 | 过程中持续进行 |
| 输出 | **验收的可交付成果** | **核实的可交付成果** |

> 顺序关系：**先控制质量（核实）→ 再确认范围（验收）**。

**工具：检查**（inspection）——测量、 examine、验证工作产品的活动，也叫审查、产品审查、审计、巡检。

**若验收不通过**：记录原因 → 提出变更请求（缺陷补救）→ 返工 → 重新提交验收。

---

### 9.7 控制范围

**核心**：监督范围状态，管理范围基准变更。

**两大失控现象（案例高频）**

| 现象 | 定义 | 后果 |
|---|---|---|
| **范围蔓延（Scope Creep）** | **未经控制**地增加特性/功能，未走变更流程 | 工期延误、成本超支、团队加班 |
| **镀金（Gold Plating）** | 团队**主动**添加客户未要求的额外功能 | 浪费资源，同样属于范围失控 |

> 共同点：**两者都不是客户通过变更流程正式批准的**。区别在提出方——蔓延多为客户/干系人逐步渗透，镀金是团队自己加的。

## 四、高频易错对照表

| # | 陷阱 | 正解 |
|---|---|---|
| 1 | 范围管理计划包含需求变更流程 | 需求变更流程在**需求管理计划**中 |
| 2 | 需求管理计划是收集需求的输出 | 是**规划范围管理**的输出 |
| 3 | WBS 分解的是活动 | WBS 分解**可交付成果**，活动由进度管理分解 |
| 4 | 工作包还可以继续分解为子工作包 | 工作包是最底层，再往下的叫**活动** |
| 5 | 确认范围由项目团队内部完成 | 由**客户/发起人**验收，属外部行为 |
| 6 | 确认范围输入是"可交付成果" | 输入是"**核实的**可交付成果" |
| 7 | 控制质量输出验收的可交付成果 | 控制质量输出"**核实的**"，确认范围输出"**验收的**" |
| 8 | 范围基准只包含 WBS | 范围基准 = **范围说明书 + WBS + WBS 词典** |
| 9 | 范围说明书列明"要做什么"就够了 | 必须有**除外责任**，明确不做什么 |
| 10 | 范围蔓延和镀金是一回事 | 蔓延来自**客户渗透**，镀金是**团队自行添加** |
| 11 | 收集需求的输出是需求管理计划 | 输出是**需求文件**和**需求跟踪矩阵** |
| 12 | 原型法用于验证设计 | 主要用于**收集需求**、澄清不明确的需求 |
| 13 | 100% 原则允许子项之和小于父项 | 必须**恰好等于**，多或少都错 |
| 14 | 分解越细越好 | 过度分解会增加管理成本，**适度即可** |

## 五、案例题万能模板

```
问题：
1. 未制定范围管理计划/需求管理计划，需求收集不充分
2. 范围说明书缺少除外责任，边界不清
3. 未创建 WBS 或 WBS 分解不到位，工作包不明确
4. 范围变更未走整体变更控制流程（范围蔓延）
5. 团队自行添加未要求的功能（镀金）
6. 可交付成果未经验收即移交，或未做确认范围
7. 缺少需求跟踪矩阵，需求无法追溯

措施：
1. 编制范围管理计划与需求管理计划，明确流程与责任人
2. 使用访谈、原型法、引导式研讨会充分收集需求，形成需求文件与 RTM
3. 定义范围时明确除外责任，获得干系人签字确认
4. 按 100% 原则创建 WBS，编制 WBS 词典，形成范围基准
5. 建立变更控制流程，所有范围变更书面申请并评估影响
6. 每个可交付成果完成即组织确认范围，形成验收记录
7. 用需求跟踪矩阵持续跟踪需求的实现与验证状态
```

## 六、论文要点（论范围管理）

**结构**：背景 300 字 → 过程论述 1500 字 → 问题与解决 400 字 → 总结 200 字

**必须体现的加分项**
- **一次范围蔓延的真实经历**：客户逐步加需求 → 如何用变更流程拦住 → 影响分析数据（工期 +20 天、成本 +12 万）
- **WBS 的实战价值**：分解到几层、工作包粒度、如何支撑估算与责任分配
- **需求跟踪矩阵的落地**：如何从需求追溯到测试用例
- **除外责任的作用**：明确写"本期不含 xx"，避免后期扯皮

## 七、60 秒自测

1. 产品范围和项目范围的区别？
2. 范围管理计划与需求管理计划分别包含什么？
3. 需求跟踪矩阵的作用？
4. 项目范围说明书的 6 项内容？
5. WBS 分解的对象是什么？最底层是什么？
6. 范围基准由哪三部分组成？
7. 确认范围与控制质量的区别与顺序？
8. 范围蔓延与镀金的区别？

<details>
<summary>答案</summary>

1. 产品范围=产品的特性与功能（看需求文件）；项目范围=为交付产品必须完成的工作（看 WBS）。
2. 范围管理计划=如何定义/创建/维护/确认范围与 WBS；需求管理计划=如何收集/分析/记录/管理需求与需求变更配置。
3. 把每个需求从来源追溯到可交付成果，确保需求被实现并验证。
4. 产品范围描述、可交付成果、验收标准、除外责任、制约因素、假设条件。
5. 可交付成果；最底层是工作包（往下是活动，属进度管理）。
6. 项目范围说明书 + WBS + WBS 词典。
7. 确认范围=客户验收（外部，输出验收的可交付成果）；控制质量=内部核验（输出核实的可交付成果）。顺序：先核实后验收。
8. 范围蔓延=客户/干系人未经变更流程逐步增加需求；镀金=团队主动添加客户未要求的额外功能。
</details>
